# Phase 0 — Recon, legitimate processes, baseline and matrices

Goal: know exactly what the system does, and how it is really used, **before** judging what it does wrong. Without this phase, Phase 4 (compatibility) is impossible. All outputs go to `security-audit/`.

Use the `security-sweeper` subagent for the mechanical inventories (0.4 especially); you review and consolidate.

## 0.1 Technical inventory → `00-recon.md`

- Languages, frameworks and versions, package managers, monorepo or multi-repo.
- Services: web, API, workers, cron, queues, realtime, edge/serverless, automations (n8n, scripts), mobile apps, admin panels.
- Databases and storage: engine, ORM/client, **where authorization is enforced** (RLS? service layer? nowhere?), buckets and their policies.
- External integrations: each third-party API, what goes in and out, which credential it uses, how it authenticates in both directions (incoming webhooks included).
- Infra: hosting, reverse proxy, PM2/systemd/Docker, open ports, TLS, firewall, admin panels, backups.
- CI/CD: pipelines, CI secrets, who can deploy, artifact signing.
- Environments: dev/staging/prod and how (or whether) they are separated.
- Environment variables: names only, where they load, which reach the client, and which environment each `.env` targets (from `00-env-targets.md`).
- AI features (if `AI_DETECTED=yes`): just list them here; the AI module builds the full inventory.
- AI development tooling committed to the repo: `.mcp.json`, `.claude/`, `.cursor/`, `.cursorrules`, `CLAUDE.md`, `AGENTS.md`, MCP server configs.

## 0.2 Legitimate process map → `processes.md`

This list protects the system from you. One process per row, IDs `P-01`, `P-02`…

| Field | Content |
|---|---|
| ID / Nome | `P-07 Recebimento de webhook da integração X` |
| Ator | usuário final / admin / operador do tenant / sistema externo / job interno / agente de IA |
| Gatilho | ação do usuário, cron, evento externo, deploy |
| Entrada → Saída | what comes in, what goes out, side effects |
| Componentes | endpoints, functions, tables, buckets, queues, external services |
| Credencial usada | anon key, service role, user token, integration API key, none |
| Criticidade | bloqueia receita / bloqueia operação / degrada experiência / cosmético |
| Evidência de uso | log, execution record or data proving the process really happens |
| Volume | typical and peak (webhooks/min, uploads/day, concurrent users) |
| Como verificar | command, script, test or manual step that proves it works |

Mandatory "invisible" processes — the ones security fixes break most often:
- Incoming webhooks and callbacks (integrations, payments, OAuth, push), including burst/batch deliveries.
- Healthchecks, status endpoints, metrics.
- Cron, background jobs, incremental syncs, reprocessing.
- Realtime subscriptions and broadcast channels.
- Service-key flows (migrations, seeds, automations).
- Mobile apps, including old versions still installed in the field.
- Long-lived sessions and shared devices (reception tablets, TV panels, kiosks).
- Real uploads (formats, sizes and names real users send).
- Multi-tenant / white-label: custom domains, themes, per-tenant configuration.
- AI features: chatbot conversations, tool calls the agent makes, scheduled AI jobs.
- Deploy, rollback, backup and restore.

Ask the user to confirm the list and add what is missing — one question, at the end of 0.2, with the list attached. Processes the user names but the code does not show are findings in themselves (dead feature or hidden component).

## 0.3 Real-usage baseline → `00-baseline.md`

What is "legitimate" is proven with data, not assumptions. Collect from available logs (reverse proxy, PM2/systemd, database/auth platform logs, automation executions, hosting platform), over the longest window available — ideally one full monthly cycle:

- Routes and functions actually called, by which kind of actor; routes that exist but never appear.
- Real origins (`Origin`/`Referer`) and domains, tenant domains included.
- User agents and mobile app versions still in use.
- Request rate per IP, user and key at peak (p95/p99), highlighting IPs shared by many users (gym or office NAT, mobile carriers).
- Real upload sizes, types and names.
- Webhook bursts (events per second at peak) and cron/job schedules.
- For AI features: messages per user per day, conversation length, tokens/cost per day, tool calls per conversation.

Use scripts or the sweeper subagent to aggregate logs; never paste raw logs into the conversation. If logs are not available, record the gap: any control that depends on this calibration (rate limit, CORS, upload validation, AI quotas) can only ship in report-only mode until data exists.

## 0.4 Attack surface → `00-surface.md`

- **Mechanical** inventory of entry points, generated by searching the code, not by sampling: API routes, route handlers, server actions (`"use server"`), edge/serverless functions, database RPCs and exposed functions, automation webhooks, chatbot endpoints, MCP servers, deep links. Record the count: "N found → N classified (public / authenticated / admin / internal)". `sizing.sh` gives starting counts.
- All inputs: forms, JSON, query, headers, cookies, uploads, webhooks, queue messages, files read from disk, integration data, LLM output.
- All outputs: email, notifications, third-party calls, generated files, logs, LLM prompts (data sent to AI providers).
- Where each credential lives, who can read it and where it travels.

## 0.5 Roles, tenants and authorization matrix → `authz-matrix.md`

- Each role and what it **should** be able to do (sources: code + docs + inference marked as such; doubts become questions to the user, not assumptions).
- Multi-tenant model: how the tenant is identified on each request and where isolation is enforced (database, service, frontend).
- Matrix **role × resource × action → allowed/denied**, with "anonymous", "user of another tenant" and "AI agent acting for user X" as roles. Include legitimate roles that see beyond their own scope (multi-unit manager, internal support, consolidated reports): without them, fixing an apparent leak breaks a real feature.
- This matrix generates the authorization tests in Phase 5.

## 0.6 Coverage matrix → `coverage.md`

Rows: every component from the inventory (service, app, database, bucket, automation, server, pipeline, AI feature). Columns: domains 3.1–3.17. Each cell: `verificado` (with method), `N/A` (reason) or `lacuna` (reason). Domains outside the approved plan are `fora do plano`. The audit ends only with zero empty cells — that is what proves the whole system was covered.
